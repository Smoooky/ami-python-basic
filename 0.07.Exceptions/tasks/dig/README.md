# dig

Данные, которые программа читает не из своего кода — из файла с сохранением
игры, из выгрузки с сайта, — это вложенные словари и списки. Нужного поля в них
может не оказаться: пользователь не указал город, у заказа нет ни одной позиции,
а вместо словаря лежит `None`. Достать `data["user"]["address"]["city"]` в лоб
нельзя: любое из трёх обращений уронит программу. Проверять каждый шаг заранее —
это лесенка из `if`, где полезного кода меньше, чем проверок.

Второй способ — попробовать и разобрать обломки. В Python его называют EAFP,
«easier to ask forgiveness than permission»: проще извиниться, чем
отпрашиваться. Пишем прямое обращение, а неудачу ловим блоком `except` — в
успешном случае, а он основной, не тратится ни одной лишней проверки.

Вопрос только в том, что именно ловить. Нет такого ключа — `KeyError`, слишком
короткий список — `IndexError`; эти двое родня, у них общий предок
`LookupError`. А если на месте словаря окажется число или `None`, будет
`TypeError`: такие объекты вообще не умеют индексироваться. Он из другой ветки
иерархии, и про него забывают чаще всего.

## Что реализовать

* `dig(data: Any, path: list[Any], default: Any = None) -> Any` — пройти по
  вложенной структуре, делая на каждом шаге `data[шаг]`. Если какой-то шаг не
  удался — вернуть `default`. Пустой путь означает саму структуру;
* `has_path(data: Any, path: list[Any]) -> bool` — существует ли путь целиком;
* `flatten(data: Any, paths: dict[str, list[Any]]) -> dict[str, Any]` — достать
  сразу несколько полей и разложить их в плоский словарь. Имена берутся из
  ключей `paths`, порядок сохраняется. Поля, которых нет, в результат не
  попадают.

Шаги пути не проверяются заранее: строка — обычно ключ словаря, целое число —
обычно индекс списка, но `{1: "раз"}` и отрицательные индексы работают сами
собой, если ничего не выдумывать.

**Ловушка со значением `None`.** Через `dig` выразить `has_path` не получится:

```python
data = {"city": None}  # поле есть, но пустое
dig(data, ["city"]) is None  # True
dig(data, ["missing"]) is None  # тоже True
```

Разница между «города не указали» и «поля нет в ответе вообще» на практике
важна. Значение по умолчанию нельзя выбрать так, чтобы оно ни с чем не совпало:
`None`, `0`, `""`, `-1` — всё это когда-нибудь окажется настоящими данными. Зато
можно создать объект, которого нет больше ни у кого: `object()` равен только
самому себе. Такой объект называют сторожевым (sentinel) и сравнивают через
`is`. `flatten` натыкается на ту же ловушку: поле со значением `None` должно
попасть в результат, а отсутствующее — нет.

## Примеры

```python
response = {
    "user": {"name": "Алиса", "address": {"city": "Москва"}},
    "items": [{"title": "книга", "price": 500}, {"title": "ручка"}],
    "note": None,
}

dig(response, ["user", "address", "city"])  # "Москва"
dig(response, ["items", 0, "price"])  # 500
dig(response, ["items", -1, "title"])  # "ручка"
dig(response, [])  # сам response

dig(response, ["user", "phone"])  # None
dig(response, ["items", 99, "title"])  # None
dig(response, ["user", "name", "first"])  # None — строку строкой не индексируют
dig(response, ["user", "name", 0])  # "А" — а числом вполне
dig(response, ["user", "phone"], default="—")  # "—"

has_path(response, ["note"])  # True, хотя значение None
has_path(response, ["missing"])  # False
has_path(response, ["items", 1, "price"])  # False

flatten(
    response,
    {
        "имя": ["user", "name"],
        "город": ["user", "address", "city"],
        "телефон": ["user", "phone"],
        "заметка": ["note"],
    },
)
# {"имя": "Алиса", "город": "Москва", "заметка": None}
```
